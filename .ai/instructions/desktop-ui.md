# Desktop App Instructions

Use this file when touching `src-tauri` (the Tauri shell, crate `ragin-dms-desktop`) or `ui` (the React webview).

## Layers

```text
ui/src (React 19 + TypeScript)    presentation state only: selection, open popovers, drafts, focus, keys
  │  typed commands + events (ui/src/ipc/bindings.ts, generated by tauri-specta)
src-tauri/src (Rust)
  ├─ context/                     AppContext: services, open catalog, last scan, cached dashboard; composition root
  ├─ session/                     the session: lanes, operations, progress, log
  ├─ messages.rs                  the words for every use case outcome
  ├─ features/<area>/             commands, DTOs and presenters of one screen area
  └─ commands/, menu.rs, protocol.rs, events.rs, crash.rs   the shell
dms_application                   use cases (see domain-application.md)
```

The app runs on **macOS, Windows and Linux**. Browser and mobile targets are out of scope; `npm --prefix ui run dev:mock` runs the UI in a browser with mock data for development only.

## Where logic goes

- Anything that derives state from the catalog, the dashboard or other domain types (filters, facets, groups, rows, task texts, counts, statistics, validations with domain rules) is a **presenter** in Rust: a pure function in `features/<area>/view*` that takes the catalog and the view parameters and returns a DTO, unit-tested with a synthetic catalog. React sends its view parameters (selection, filters, query, sort) and renders the DTO.
- Pure UI state (what is selected, which popover is open, a draft being typed, keyboard handling, the drag pointer) stays in React.
- Do not re-implement domain rules in TypeScript. Names and dates the user typed are checked in Rust with the domain constructors (`TagName::parse`, `RelativePath::parse`), which return the 1.x messages.
- The composition root (`context/composition.rs`) is the only place that builds adapters and `AppServices`. Commands get everything through `AppContext`; no globals.

## Rust rules (`src-tauri`)

- Module layout per area: `features/<area>/mod.rs`, `commands.rs` (or `commands/`), `dto.rs` (or `dto/`), `view.rs`/`view/` (presenters, with their tests beside them). At most 8 source files per directory.
- Commands are thin: `#[tauri::command] #[specta::specta]`, parse input, call one use case or presenter, map to a DTO. Register them in `collect_commands!` in `main.rs`. Blocking use cases run in `tauri::async_runtime::spawn_blocking` or inside a session operation, never on the main thread.
- Commands resolve documents by id or library-relative path, never by an absolute path from the window. Parse input ids and paths with the domain constructors and return `IpcError::invalid(..)` on bad input.
- DTOs: `#[derive(Debug, Clone, Serialize, Deserialize, Type)]`, `#[serde(rename_all = "camelCase")]`; ids and relative paths as `String`, dates as `YYYY-MM-DD`, instants as RFC 3339, enums as camelCase strings, enums with data as `#[serde(tag = "kind")]`. Domain types never cross IPC. DTO and command names are global in the bindings: prefix them with the area.
- After changing commands, events or DTOs, regenerate the bindings: `UPDATE_BINDINGS=1 cargo test -p ragin-dms-desktop export_bindings`. Never hand-edit `ui/src/ipc/bindings.ts`.
- Phrase use case outcomes only in `messages.rs`. A `match` over `OpenTask`, an outcome type, `StorageFailure`, `CatalogRejection` or the library status names every variant, also in helpers, never `_ =>`.
- Panics show the "Ragin-DMS stopped working" dialog (`crash.rs`) and close the app; that is the last resort, not error handling.

## The session

- `session::Session` is the one owner of running operations: `ctx.session.perform(label, lane, cancellable, job)` runs one operation at a time per `Lane`: `Library` for everything that changes files or the catalog, `Ai` for the AI's runs, which only add suggestions and so run beside library operations. `perform` returns `false` when the lane is busy; the command then reports that the user should wait. Screens disable a button only while its own lane is busy.
- Session operations of the open library live on `AppContext` (`open`, `scan`, `reopen`, `rescan`, `analyze_inbox`, `update_preferences`, sync, merge, retry). Call them; never duplicate them in a feature.
- Long operations report progress (`op.progress(...)`: step, done of total, current item) apart from the session state, so screens do not re-render on every file. Only operations that leave the library consistent wherever they stop are `cancellable` (a scan, adopting many files). Cancel is offered in the status bar and the menu.
- After an operation changed the library, `session.changed()` tells the window to reload its queries.
- `SessionLog` keeps the last lines of what the app did in this session for the log panel. It is not written to disk.
- `update_preferences` is the one writer of the device preferences (layout, AI settings). Every persisted setting has one writer; the UI never writes settings files.
- A scan with the preference "Add new files while scanning" catalogs new files of the primary in batches while it runs, so the library fills up live; files only the sync folders have are adopted right after the scan.

## TypeScript rules (`ui`)

- Feature folders: `ui/src/features/<area>` (`dashboard`, `library`, `document` (quick look, details, review, assistant), `inbox`, `settings`, `restructure`, `ask`, `pdf`). Each area has one CSS file and an `index.tsx` that exports what other areas may use.
- Shell: `ui/src/shell` (app shell, `navigation`, `palette` (⌘K / Ctrl+K), `status` (the status bar with library state, folders online, running operations with progress, Cancel and Log), `toolbar`, `screens.ts` with `goTo`/`takeRequest`). Session state and operations: `ui/src/session`. Shared: `ui/src/shared` (`components`, `format`, `hooks`, `platform.ts`).
- Reads through TanStack Query with keys starting with `LIBRARY_QUERY`, so a finished operation reloads them. Actions are plain command calls with `.catch(reportError)`.
- Use the shared components first (`shared/components`: buttons, fields, menus, tooltips, dialogs, cards, thumbnails). Confirmations and text input go through the promise-based dialogs (`dialogs.confirm`, `dialogs.askText`).
- Platform wording and keys come from `shared/platform.ts` (`commandKey`, `shortcutLabel`, `fileManagerName()`): "Show in Finder" on macOS, "Show in Explorer" on Windows, "Show in file manager" on Linux; ⌘ on macOS, Ctrl elsewhere.
- Dates go through `shared/format/dates.ts` (absolute `YYYY-MM-DD`, relative in words with the exact date in a tooltip), sizes through `shared/format/sizes.ts`.
- Pictures load through the `dms://localhost/` protocol (`thumb/…` for thumbnails, `page/…` for PDF pages) via `PageThumbnail`; a missing picture shows the fallback.
- Internal drag and drop (documents onto folders) uses pointer events, never HTML5 drag and drop. Files from the file manager come from the webview's drag-drop event (position + paths) and are added like files from the file picker: in the library to the selected folder, on the dashboard to the top level.
- Mocks: every command has an answer in `ui/src/mocks/handlers/<area>.ts` from the synthetic `mocks/fixture.ts`, so `dev:mock` shows every screen.

## The dashboard

The dashboard is the home screen and the **only place where detected changes become actions**.

- It shows the library folders with their status, the open tasks (`OpenTask` from `BuildDashboard`), bulk actions (categorize all new, sync to all destinations, merge all folders) and recent activity.
- It is also the entry point into the library: quick access by category and tag (a click opens the library filtered by it), recent documents, and statistics (documents per year, kind, category and correspondent). The figures are computed by presenters from the catalog (`features/dashboard/view`); components never count documents themselves.
- Every task row offers the actions its use case supports, and nothing else. The buttons are computed in Rust; the `match` over `OpenTask` is exhaustive.
- An AI suggestion is approved field by field or as a whole, and every value is editable before approval. There is no "apply automatically" path. The suggested file name starts checked only when `AiSettings::accept_suggested_file_names` is on.
- Bulk approval is always an explicit click on a selection the user can see.
- A task disappears only when its use case succeeded or the user dismissed it.
- "Needs your attention" shows at most 5 rows by severity, each severity also named in words.

## The library

- The sidebar holds views (All documents, Inbox, Needs review, Added this month, Folders, Saved views; no Trash, trashed documents are in the system trash), foldable to a rail and resizable. Panel widths are device preferences and go through `update_preferences` only.
- All filters are facet filters in the library's view parameters, applied only by the library presenter, shown both as tokens in the search field and as facet chips. Type and Needs review cannot be a `DocumentQuery`, so saving or exporting such a view is refused with a reason.
- Documents show grouped in a grid or list, can be ticked for the bulk bar, and open in one quick look. Keys: "/" to search, Space for quick look, arrows for next/previous; every shortcut is also in the Documents menu.
- Text search runs `SearchContents` after a typing pause while its switch is on; it only reads, so it never waits for a lane.
- Drag targets are folders (tree, tile, breadcrumb). Every drop target highlights while a document hovers over it and names what the drop will do. A drop that changes nothing does nothing.

## AI is optional

AI is optional per device (`AiSettings::enabled`, "Use AI" in Settings › AI, sent to the window as `aiEnabled` in the session state). While it is off, no AI feature is shown: Ask in the navigation, the AI band and inbox analysis on the dashboard, the inbox AI actions and their settings, the AI actions of the quick look and the bulk bar, "Convert to real PDF", and the AI actions of the toolbar and the palette. A new AI feature must hide the same way.

## Errors and feedback

- Use case outcomes are data. Map every outcome variant to a message or state; never `_ =>`.
- **A refused action says why.** A disabled button carries a tooltip with the reason; a refused drop shows the reason in the status bar. A silent refusal is indistinguishable from a bug.
- Destructive actions (trash, delete everywhere, keeping one side of a conflict, deleting a folder, category, tag or saved view, applying or reversing a restructure) always ask for confirmation and name the affected files and folders.
- Unrecoverable errors (primary folder missing, catalog unreadable) are shown in a dedicated error state with a way to fix them (choose the folder again, open the conflict copy), never as a crash.
- An offline sync folder is a status, not an error.

## Design system

- Light and dark theme following the system setting, Material 3 metrics. Colours, spacing, shapes and the type scale are CSS variables in `ui/src/styles/theme.css`; use them, never hex colours or ad-hoc sizes in components. The type scale is set in Geist, bundled in `ui/src/assets/fonts` with its licence (`geist-OFL.txt`).
- Icons: Material Icons round (`@material-design-icons/svg/round/<name>.svg?raw` with the shared `Icon`).
- `--ai-gradient` is only for what the AI does (AI band, AI suggestion card, AI buttons) and the logo.
- Charts follow fixed rules: a fixed colour order (never cycled), thin marks, a legend with counts, and labels only where they help. Status colours are reserved for states and never used as a chart colour; a state also carries an icon or a label, never colour alone.
- Short labels (tags, chips, file sizes, folder names) do not wrap and truncate with an ellipsis.
- Keyboard first: every main action has a shortcut and a menu entry (`menu.rs`: Library, Edit, Documents, View); the review supports approve → next without the mouse. The Edit menu (undo, redo, cut, copy, paste, select all) exists because the webview needs it on macOS; keep ⌘A / Ctrl+A in text fields selecting text and outside them ticking all documents.
- The app icons live in `src-tauri/icons/`.
- Texts the user reads are the 1.x texts; keep wording consistent with the existing screens.
